- 評価日: 2026-07-31
- 対象: Web版、macOS版
- 状態: 主要構成を実装済み。対象テストと実画面レビューを通過し、全体回帰と
  物理支援技術の確認を継続中
- 正本の範囲: 「空」と「現象」をまたぐ画面構成、狭幅時の優先順位、再レビュー方法

天文計算と現象予報の意味・精度契約は既存のユーザーストーリーと精度文書を
維持する。この文書は、それらを一つの画面へ詰め込まず利用できるようにする
情報設計だけを定める。

## 改善前の実測と問題

| 条件 | 観察 | 利用者への影響 |
| --- | --- | --- |

## 合意する共通IA

第一階層を次の二画面とする。

1. **空** — 星空、恒星検索、選択恒星の要約、時刻操作を扱う。
2. **現象** — 予報条件、現象一覧、選択した現象の詳細を扱う。

地点と観測日時は両画面で共有する。「選択時刻を空に表示」は明示操作として
観測日時を更新し、「空」へ移動する。単なる画面切替では日時、地点、選択恒星、
選択現象、フィルターを変更しない。現象用コードとデータは、初めて「現象」を
開いた時だけ読み込む。

表示設定、ヘルプ、精度・プライバシー説明は主画面と同列に縦積みせず、
ダイアログ、sheet、Settings scene、折りたたみ詳細などの二次面へ置く。安全上
必須の日食注意と、判断に必要な不確実性は折りたたまず、対象の現象詳細に残す。

### Web

- 「空」「現象」の主ナビゲーションを画面本文より先に置く。
- 「空」は星図を主領域、恒星検索と要約を補助領域とする。
- 「現象」は予報一覧と現象詳細で主領域を使い、星図の右32%へ押し込まない。
- モバイルの「現象」は、星図と時刻レールを通過せず、地点・期間・結果状態から
  始める。
- 画面切替後は、新画面の見出しへfocusを移すか、支援技術へ同等の文脈変更を
  通知する。非表示画面へtab focusを残さない。

### macOS

- `NavigationSplitView`の第一階層で「空」「現象」を選べるようにする。
- 「空」は恒星一覧、星図、任意の補助Inspectorという役割分担を維持する。
- 「現象」は一覧をsidebar、選択した現象をdetailへ置く。270–390ptのInspectorは
  補助情報に限り、接触表や安全注意を含む現象詳細の主置き場にしない。
- Settings scene、Help、Inspectorの表示有無が変わっても主画面の選択を保つ。

## 実装済み

### Web

- `/sky`と`/events`を直接開ける型付きrouteとし、履歴の進む／戻る、画面名、
  focus移動を主ナビゲーション「空」「現象」と同期した。
- 現象機能は初めて開いた時に遅延読込する。画面切替だけでは地点、日時、
  選択、フィルターを変更しない。
- 960 CSS px未満では現象一覧から詳細へ進む一画面ずつのdrill-down、960px以上では
  一覧と詳細の二列表示とstickyな一覧を採用した。長い現象名は省略せず折り返す。
- 現象詳細は最大／最接近と主操作の直後に接触時刻を置き、シミュレーションと図を
  その後へ移した。
- 現象の時刻を「空」に反映した時は、現象名と表示時刻、「現象へ戻る」、
  「元の日時に戻る」を文脈バーに残す。
- 通常時の計算状態は一行へ短文化し、完全なモデル名と適用条件は「計算情報」で
  開示する。準備中、失敗、近似警告は短文化の対象外とする。

### macOS

- `NavigationSplitView`の第一階層を「空」「現象」に分けた。
- 「現象」は`EventWorkspace`として一覧をsidebar、選択内容をdetailへ置き、
  狭いInspectorだけに現象詳細を載せない構成へ移した。
- 詳細は最大／最接近、接触時刻、シミュレーション、精度情報の順にし、
  観測判断に使う時刻を図より先に読めるようにした。
- 「空」の通常時の計算状態を短文化し、詳細条件は必要な時に確認できる階層を
  維持した。

## 情報密度の規則

- 各画面の先頭は「何を見る画面か」「どの地点・日時か」「次に行う主操作」を
  優先する。
- 平易な要約と主要値を先に置き、モデル、データ版、誤差予算、JSONは
  「精度と条件」「再現情報」へ段階化する。
- 同じ地点・日時・精度注意を複数パネルで重複させず、一つの現在状態を参照する。
- 長文でレイアウトを埋めず、見出し、定義リスト、表を使う。ただし文章で伝える
  安全注意と不確実性をアイコンやtooltipだけへ置き換えない。
- 選択前、読込中、結果なし、失敗、選択済みの各状態で、空の大きな枠や
  レイアウトの跳躍を作らない。

## P0受け入れ条件

1. WebとmacOSのどちらも、起動直後から「空」「現象」の主画面を識別して移動できる。
2. Webの861、900、1024、1440 CSS pxで、主要操作、星図の方位、一覧、表に
   横方向の見切れ、意図しない横スクロール、コンポーネントの被りがない。
3. Webの390×844で「現象」を開くと、最初のビューポートに画面見出し、地点・期間、
   読込／空／結果のいずれかが現れ、星図を先にスクロールする必要がない。
4. 390 CSS pxおよび200%ズームで主ナビゲーションと主要操作を利用でき、
   24px未満の操作対象を作らず、主要対象は44pxを目標にする。
5. macOSの現象詳細はdetail領域に表示し、270–390ptのInspector幅だけへ
   制約しない。最小対応ウインドウでも接触表と主操作が重ならない。
6. 主画面の切替だけでは地点、日時、再生状態、選択、フィルターを暗黙に変更しない。
   「選択時刻を空に表示」だけが既存契約どおり日時を変更する。
7. キーボードだけで主画面、検索／予報条件、一覧、詳細、戻る操作へ到達できる。
   focus順は見た目と一致し、非表示画面へ移動しない。
8. 一般向け要約と主操作が、精度・再現情報の長文より先に現れる。日食の安全注意と
   境界付近の不確実性は省略・折りたたみしない。
9. 「現象」を開くまで現象chunkを取得せず、初期転送量、既定2D・停止、無音、
   権限を自動要求しない契約を維持する。
10. 読込中、結果なし、失敗、選択済み、狭幅、拡大の各状態を実画面で確認し、
    console警告・エラーとアクセシビリティ上の名前欠落を残さない。

## 検証済み

- Webはroute単体／統合テストで直接URL、`pushState`／`popstate`、選択保持、
  focus移動、現象chunkの遅延読込を確認した。
- Webの現象一覧と詳細は390×844、900px、1440pxで実画面を再測定し、狭幅の
  一覧→詳細、デスクトップ二列、sticky一覧、長い名称、接触時刻の順序、
  意図しない横スクロールがないことを確認した。
- Webの文脈バーと計算情報はコンポーネント／App統合テストと実ブラウザー操作で、
  戻り先、元日時の復元、開閉、表示順を確認した。
- macOSは`NavigationSplitView`、`EventWorkspace`、接触時刻の優先順、短い計算状態を
  Swiftの対象テストとbuildで確認した。
